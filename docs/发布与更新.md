# 构建、发布与更新

## v0.1.1 更新行为

macOS ARM64 和 Windows x64 外网端每天按本机时间 01:00 检查 GitHub 正式版本。应用启动或电脑唤醒后补查最近未完成的检查窗口，不主动唤醒电脑、不安装系统计划任务。失败按 1、5、15、60 分钟重试；用户可随时手动检查。

左下角显示实际构建版本、候选版本、检查/下载/可安装/失败状态；外网另外显示更新包投递状态。后台检查不弹窗，点击“更新”才确认目标版本和说明。普通任务及更新投递未完成时先等待，不中断正在执行的传输。

更新包先缓存到专用应用数据目录，确认前不进入 Sparkle 或 Velopack 安装流程。macOS 关闭 Sparkle 自带自动检查和自动安装，仅在用户点击后启动固定版本的原生更新确认界面；必要时会再次通过 HTTPS 下载 ZIP。Windows 用户确认后才从已验证缓存进入 Velopack 安装，启动时还需版本/清单摘要对应的授权记录与单实例锁。

## 外网转发与内网接收

外网发现正式发行后，独立下载本机更新以及 Windows 完整更新包、更新索引和签名清单；即使 macOS 自己已是最新版，也继续检查和补发 Windows 更新。外网是否安装自身更新不影响转发。

更新专用目录为：

```text
<现有 FTP 目录>/shanchuan_updates/stable/win-x64/<版本>/<投递批次>/
```

先上传更新包和索引，最后上传清单和签名。未完成批次不会作为可用更新。每次投递有独立批次，失败保留本地任务并重试；普通传输优先，更新任务在普通任务之间执行。

内网 Windows 不访问 GitHub，按现有接收轮询间隔从专用目录发现更新，只列表和下载，不删除共享更新文件。因此同一 FTP 目录下多台内网电脑可以分别更新。更新文件不写入剪贴板、普通历史或用户配置的普通接收目录。远端旧更新包由服务器管理员按需要维护；外网程序不新增下载、删除权限。“已投递”只表示 FTP 上传完成，不表示内网已安装。

## 签名信任与正式发布

每个正式发行附带 `update-manifest.json` 和 `update-manifest.sig`，后者是对清单原始 UTF-8 字节执行 ECDSA P-256/SHA-256 的 DER 签名。清单记录版本、发布通道、产品和各附件的平台、架构、用途、名称、字节数、SHA-256。客户端内置公钥，外网和内网均验签、校验包内容、验证索引与目标版本一致，拒绝降级和未知平台。FTP 自身的 MD5 或同目录校验文本不能替代签名。

发行签名私钥和 Sparkle 私钥仅存储在 GitHub Actions Secrets。仓库只包含公开验签材料；测试使用独立公开样例和临时生成的测试私钥。

| GitHub 配置 | 内容 |
| --- | --- |
| Secret `UPDATE_MANIFEST_PRIVATE_KEY` | P-256 发行签名 PEM 私钥 |
| Secret `SPARKLE_PRIVATE_KEY` | Sparkle Ed25519 私钥种子（base64） |
| Variable `SPARKLE_PUBLIC_KEY` | 与仓库 `Resources/sparkle-public-key.txt` 对应的公钥 |
| Secret `MACOS_CERTIFICATE_P12` | Developer ID Application 证书和私钥导出 P12 的 base64 |
| Secret `MACOS_CERTIFICATE_PASSWORD` | P12 密码 |
| Secret `APPLE_ID` | 公证账户 |
| Secret `APPLE_TEAM_ID` | 开发者 Team ID |
| Secret `APPLE_APP_PASSWORD` | Apple 应用专用密码 |

更新清单公钥位于 `Resources/update-public-key.pem`，编入两端应用；Sparkle 公钥随 macOS 包嵌入。下载地址由仓库 `DB-XiaoQiang/shanchuan` 和版本标签自动生成，无需逐次手填 URL，不嵌入 GitHub 访问令牌。

正式发布必须满足双端测试、macOS Developer ID 签名与公证、Sparkle 包签名和发行清单签名。缺少必要条件时，稳定通道只生成草稿，不成为客户端的正式更新源。用户可明确选择公开预发布，提供测试包下载，但不生成稳定更新清单。普通 CI 产物明确为未正式签名测试包；Windows 尚无 Authenticode 发行证书。

## 发布通道

`RELEASE_CHANNEL` 必须由用户明确决定，可选 `draft`（草稿）、`prerelease`（公开预发布）、`stable`（正式版）。本次用户指定版本为 **0.1.1**，通道为 **prerelease**。

公开预发布使用 `--prerelease --latest=false`，不生成正式更新清单；即使以后配置了签名凭据，此通道也不会自动变成稳定版。客户端忽略预发布，正式自动更新继续关闭。普通用户可从 Releases 下载 Setup 或 DMG 进行手动测试。旧的 0.2.0、0.3.0 草稿编号不是后续自动升级版本的依据。

## 构建与发行步骤

`VERSION` 是两个平台唯一版本来源，具体版本号由用户决定，未经明确指定不修改版本号或创建标签。架构级变更增加主版本，新增功能增加中间版本，小改动与 BUG 修复增加末位版本；分类规则不代表自动递增。主分支提交、PR 和手动工作流运行发行工具测试、两端编译与测试。macOS 生成应用、DMG 和 ZIP；Windows 生成 Setup、便携包和 Velopack 完整更新包及索引。

1. 按用户明确指定的版本修改 `VERSION` 和发布通道 `RELEASE_CHANNEL`，补充 `docs/releases/<版本>.md`，提交并推送主分支。
2. 等待 CI，通过后创建并推送严格匹配的 `v<VERSION>` 标签。
3. 发布工作流按固定版本构建，完成签名、公证、appcast、签名清单和 SHA256SUMS，再创建 Release。
4. 已有 Release 的标签不覆盖；已正式发行后的修复采用新版本。失败且尚未创建 Release 时可手动重跑该标签。

## 首次安装与升级验收

v0.1.1 是首个完整更新协议版本。旧版本未配置更新源且没有新的验签公钥，第一次必须手动安装：Windows 用 Setup，macOS 用 DMG。DMG 打开后将闪传拖至 Applications（应用程序），复制完成后推出镜像；升级前等待传输结束并退出闪传。

之后用两个连续正式构建验证：外网发现下载、FTP 多端投递、内网收取、左下角提示、明确确认、等待任务结束、重启升级，以及配置/密码/历史/系统权限保留。回环 FTP 测试不会连接真实服务器；实际 FTP 联调需要用户指定环境。Windows 剪贴板、热键、安装重启和 macOS 系统权限、公证必须做真机验收，不能用编译通过代替。
