# macOS 构建号

`VERSION` 仍由用户决定，对应应用展示版本 `CFBundleShortVersionString`。`CFBundleVersion` 是 Sparkle 判断更新先后的构建号，两者用途不同。

## 统一规则

普通 macOS 应用使用完整 Git 历史中的源码提交总数作为构建号：

```sh
python3 scripts/build-number.py
python3 scripts/build-number.py --repo /完整源码仓库 --revision v0.2.3
```

命令成功时只输出正整数，不修改仓库。同一源码提交在本机、CI 和版本发布中的结果相同；在保留历史、向前推进的主分支上，后继提交的计数严格增加，因此不会再出现不同发行版都使用构建号 `1` 的情况。旧版 0.2.1／0.2.2 的构建号均为 `1`，新版本使用当前完整源码计数，数值会高于 `1`。

打包脚本统一调用此命令。GitHub macOS 构建、正式发布和上传包签名准备都必须完整检出源码，即 `actions/checkout` 的 `fetch-depth: 0`；不再使用各工作流各自的 `github.run_number`。

## 显式变量与失败处理

保留 `SHANCHUAN_BUILD_NUMBER` 环境变量的校验入口，但它只能与源码派生结果完全相等。不能用固定值 `1`、手动大号或另一条流水线的运行次数覆盖，否则未来默认计数可能倒退。

浅克隆、缺失祖先提交、Git replace refs、Git grafts、未知源码提交或源码归档没有 Git 元数据时，命令直接失败，不回退为 `1`。上传包的准备流程应独立计算对应源码的预期构建号，并要求 ZIP 内 `CFBundleVersion` 精确相同。

## 发布约束

发行提交必须沿正常主分支历史向前推进，不得为发布而删除／改写已发布的历史，或从更旧的分支另行发布更高展示版本。同一提交的重新打包会保持相同构建号；需要形成新的可升级发行版时，应先提交用户批准的修改，再按用户指定的版本发布。

独立更新测试应用继续使用其显式、隔离的测试构建号参数，不改变正式应用的构建号规则，也不更改正式通道、公钥或 `VERSION`。
